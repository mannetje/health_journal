## Context

Fluid intake follows `docs/dev/how-to/add-a-metric.md` and `openspec/playbooks/add-a-metric.md`, with two differences: it is a high-frequency log (many entries a day), so the quick-add tap and the day grouping matter more than the form, and it has a second use case, a personal minimum and maximum, that no other metric has. Decisions are in [ADR 0030](../../../docs/adr/0030-fluid-intake-quick-log-with-personal-limits.md); wording rules come from [ADR 0021](../../../docs/adr/0021-medication-compliance-and-privacy.md), neutral labels and colours from [ADR 0005](../../../docs/adr/0005-dutch-nhg-guidelines.md) and the `range-labels` capability, comments from [ADR 0019](../../../docs/adr/0019-entry-comments.md), backup from [ADR 0024](../../../docs/adr/0024-portable-encrypted-backup.md), pickers from [ADR 0018](../../../docs/adr/0018-smart-input-pickers.md), localized messages from [ADR 0015](../../../docs/adr/0015-localized-viewmodel-messages.md).

## Goals / Non-Goals

**Goals:** (1) a log that costs one tap, own sizes, a plain daily total, a history grouped by day and a bar graph; (2) an optional personal minimum and an optional personal maximum, each set only by the person, shown as a neutral position label next to the total; a reference note with the Dutch sources; nothing advised; English and Dutch.
**Non-Goals:** see the proposal.

## Decisions

### 1. Domain (`:domain`)
- `FluidIntake(id, profileId, timestamp, ml, comment?)` with validation (whole ml 10 to 5000; constants in one place).
- `QuickAddSizes` value object (three slots: name, ml) with the same validation and the defaults 150, 250, 500; pure, no Android.
- `FluidLimits(minMl?, maxMl?)` value object: each value whole ml 100 to 10000 or null; when both are set, `minMl <= maxMl`, else `DomainError.Invalid` with the field and rule (ADR 0037). No default value exists anywhere in the type.
- `FluidPosition` and `fluidPosition(total, limits)`, a pure function: `NONE` when no number is set, `BELOW_MIN` when a minimum is set and `total < min`, `ABOVE_MAX` when a maximum is set and `total > max`, otherwise `WITHIN`. A total equal to a limit is `WITHIN`. Only the numbers that are set take part. No thresholds of the app's own and no Android in this code.
- A new `FluidRepositoryPort` (record, update, delete, list, list in range, read and write limits; one port per metric, see ADR 0036 and 0038), the commands `RecordFluidIntakeCommand`, `UpdateFluidIntakeCommand` and `SetFluidLimitsCommand` (both values in one command, null clears one) with one handler each, a query for the limits, and a fluid branch in `PortEntryGateway` for `DeleteEntryCommand`. Undo dispatches `DeleteEntryCommand` with the id returned by record. Handlers are registered in `CommandModule`.
- `FluidDayTotals`: groups entries by local calendar day using an injected `ZoneId` and `Clock` (no `ZoneId.systemDefault()` inside domain), returns per-day totals for a range. `FluidStatistics`: average per logged day (whole ml, round half up), highest day and date, days logged, and, given `FluidLimits`, the counts of logged days per `FluidPosition`. `FluidWeekdayAverages` (first day of week passed in), `FluidTimeOfDay` (eight three-hour blocks, average per logged day) and `FluidCalendarMonth` (the days of one month with their totals and positions) feed the weekday chart, the time-of-day chart and the calendar. Empty range yields none. No thresholds of the app's own.

### 2. Data (`:data`)
- `FluidIntakeEntity`, DAO, mapper, repository methods; table `fluid_intakes` indexed by profile and timestamp. Totals and positions are computed in `:domain` from entries and the limits, not stored: one source of truth, and editing a timestamp or a limit can never leave a stale total or label.
- **One migration, `MIGRATION_N_N+1`, where N is the current database version at implementation time**, added to the `addMigrations` list: `CREATE TABLE IF NOT EXISTS` for `fluid_intakes` and `fluid_settings` plus the index. A migration test opens a database of version N with rows and checks version N+1, old rows and empty new tables.
- **Personal minimum and maximum** in `fluid_settings(profileId PRIMARY KEY, minMl NULL, maxMl NULL)`: they must be per profile and inside the encrypted database (preferences are not encrypted and the `privacy` capability forbids health data there); a nullable column on the profile table was rejected because it would change an existing table for optional values, and a table of its own keeps the migration purely additive. A missing row or a null means "not set". Neither is in the CSV (settings, not entries); both are in the backup document as `fluidMinMl` and `fluidMaxMl`.
- Quick-add sizes in the existing preferences store (three int and three string keys), with defaults when absent or invalid.
- CSV adapter with `CsvQuoting.cell`; backup snapshot and restore include `fluidEntries`, `fluidMinMl` and `fluidMaxMl`.

### 3. App (`:app`)
- Log screen: a Fluid tab (a `FluidCard`) with three quick-add buttons, a custom entry action (opens the form with the ml field, date and time and comment with counter, using the number picker of [ADR 0018](../../../docs/adr/0018-smart-input-pickers.md)), the "Today" line ("Today: N ml", plus the person's numbers and the position label when set), a "Your limits" action opening two fields (minimum, maximum; empty until set; clear action for each; an info control for the reference note), an edit-sizes action and an Undo snackbar (about 5 seconds, announced for screen readers). The Today line is a `StateFlow` recomputed from entries and limits when the day, the entries or the limits change, and at local midnight.
- Position label: "name · range" like the range labels, from the sequential neutral ramp (below the minimum lightest, within the middle, above the maximum darkest, with the dark-mode variants), label text always present, contrast at least 4.5:1, never green, yellow, orange or red. The same label is on each day-total row in History.
- Reference note "About these amounts": a bottom sheet in the style of "About these ranges". It states, as the sources' own statements and with the source named and linked, the Voedingscentrum general adult amounts, that a maximum for a condition is set per person by the huisarts or cardiologist, and that the person asks their huisarts, with links to Voedingscentrum `vocht.aspx`, Radboudumc (Vochtbeperking) and Thuisarts. The note also says that what counts towards a restriction (soup, custard, yoghurt) differs per care team; the app does not decide that, so a person logs what their team counts. It says the app is not a medical device and sets no target, and it never writes into the fields.
- Buttons are at least 48 dp, each with a content description of the form "Add 250 ml". A double tap adds two entries by design (honest log); Undo removes only the last one.
- History: rows per entry; under the Fluid filter a day-total row above each day's entries (with the label when limits are set); filter chip, edit dialog and delete through the existing code.
- Graph view (`ui/history/charts/FluidGraphSection.kt` and `FluidCalendarCard.kt`, next to `MigraineGraphSection.kt` and `MigraineCalendarCard.kt`, reusing `BarTrendChart`, `ChartPrimitives`, `TrendBuildingBlocks`, `TrendDateRange` and the Migraine Graph/Calendar toggle and month navigation): figures, then a bar chart of day totals in one hue with the shared range, axis, zoom and minimum-data code (axis starts at 0; up to two thin dashed lines, one at the minimum and one at the maximum, only for numbers that are set, each with its number as plain text; bars never change colour), a weekday chart and a time-of-day chart. The calendar is a month grid with the total printed in each logged day, shaded in steps in proportion to the month's highest day, and one shape marker per position when limits are set; a tap on a day sets the History filter to Fluid and that day, like the Migraine calendar. All figures come from pure functions in `:domain` (`FluidDayTotals`, `FluidStatistics`, `FluidWeekdayAverages`, `FluidTimeOfDay`, `FluidCalendarMonth`, `fluidPosition`); text descriptions for screen readers carry the same numbers.
- Profile notice: one added sentence. Strings in `values/` and `values-nl/`, ViewModel text via `UiText`; a test scans the fluid strings for advice and verdict words (including "enough", "too much", "too little", "dehydrated", "goal", "target", "should", "remaining", "left", "genoeg", "te veel", "te weinig", "uitgedroogd", "doel", "moet", "overschreden"); the position label words ("below your minimum", "within your limits", "above your maximum") and the person's own numbers shown back are allowed.

### 3a. How it fits the current architecture
Fluid intake is a plain metric ([How to add a metric](../../../docs/dev/how-to/add-a-metric.md), [playbook](../../playbooks/add-a-metric.md)) with a settings table and a richer History view, and it adds no new layer, port style or dependency.

New code is therefore in the folders where a reader of the existing metrics would look for it. The one structural addition is `fluid_settings` (a per-profile settings table), which no other metric has; it follows the rule that health data and anything per profile lives in the encrypted database, not in preferences.

### 3b. What the Dutch practical advice confirms
The Radboudumc advice for people with a fluid restriction (measure your own cups and glasses, write each amount down at once, spread the amount over the day) is what the own quick-add sizes, the one-tap log, the day total and the time-of-day chart already do. The same advice says the amount is personal and the doctor sets it, which is why the fields stay empty. It names no minimum, so the minimum rests on Voedingscentrum's general amounts and on the person's own doctor, and the app takes the person's number either way.

### 4. Type of drink: later, not in version 1
Version 1 records volume only: a type would add a choice to every tap and invite nutrition framing. Planned later addition: an optional type with the default "water", added by a later migration as a nullable column that reads as water when empty, with no nutrition or caffeine framing. Old rows and backups stay valid without it.

### 5. Two use cases, two numbers, and how it stays neutral
- **Why both a minimum and a maximum.** Some people may not drink more than a set amount a day because of a condition, and the amount comes from their huisarts, cardiologist or leaflet. Others need a minimum intake. They are independent: one, both or neither can be set, so a person on a restriction sees only a maximum and a person who must keep up their intake sees only a minimum.
- **Where the numbers come from.** Voedingscentrum gives general minimums for adults (at least 1.4 litres a day from drinks; men 1.4 to 1.8), and the maximums for a condition are individual. Neither is a number the app may pick: the fields are empty with no default, hint, example or "use the Voedingscentrum value" button, because a general minimum is wrong for someone on a restriction and a restriction is wrong for everybody else. The general figures appear only in the reference note, as what the source says, and the pregnancy, breastfeeding, heat, illness and exercise variants are not turned into a computed number.
- **How it reads.** "Today: 900 ml · Below your minimum · 1400 ml". "Today: 1700 ml · Above your maximum · 1500 ml". The label names where the total stands against the person's own number, always with the number, in the manner of ADR 0005 and the `range-labels` capability (name together with range, no condition names, neutral ramp, not-a-diagnosis note). It contains no advice, warning or instruction, and no alert, notification, reminder, ring or percentage exists.
- **Compliance.** The existing `compliance` capability forbids advice and verdicts. A neutral position against the person's own number is the same kind of statement as the NHG range labels it already allows ("Reference ranges are informational and neutral"), and the colours never signal danger. The label words are therefore a deliberate, listed exception to the wording scan; this is the one point to confirm in the review (proposal, open questions).
- **Risk.** Even a plain label can read as a verdict or as a goal. Mitigated by neutral colours, the number always next to it, the reference note saying the numbers are the person's own and that the app is not a medical device, and by no reminders or alerts.

### 6. Layer rules
Rules, positions, grouping and figures in `:domain` (no Android), persistence and CSV in `:data`, screens and charts in `:app`.

## Risks / Trade-offs
- A reader may expect a goal or ring as in other water apps; the notice and the design are the intended behaviour.
- A position label can feel like a verdict; see section 5.
- Many entries per day make History long; the day-total rows and the graph are the overview. Delete of a wrong tap is by Undo or the History row.
- The daily total depends on the device time zone; a time zone change can regroup entries. Accepted, as for other daily figures; the day is the local day of the timestamp at display time.
- The current day is shown against the limits before it is over, so "Below your minimum" is normal at noon. The label is for the day so far and says nothing about the day being finished; no special handling in v1.
- Another migration adds a row to the upgrade path; covered by the migration test.

## Migration Plan
The migration is the next free number at implementation time (current database version + 1); nothing here depends on the order in which features are built.
1. Domain and tests; 2. tables, migration and repository with the migration test; 3. CSV and backup with the format docs; 4. screens; 5. emulator pass with screenshots; 6. docs, changelog and release.
Rollback: the tables are additive; Room refuses a downgrade of the version, as for every migration.

## Open Questions

- Type of drink is a planned later addition (section 4).
- Whether the Today line should also be shown on the Overview or a widget: not in v1.
